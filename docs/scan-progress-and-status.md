# Scan progress and finding status

The comparison page reads two completed, persisted scan results for the same application asset. It matches findings by canonical finding ID, then reports New, Resolved, Changed, and Persistent. Changed compares recorded algorithm, key, risk, context, confidence, and urgency fields. The risk total is the sum of persisted finding scores; unscored findings are counted separately. A resolved finding was absent from the later scan's observed scope, which should be checked before claiming remediation.

Finalized scan results and CBOMs cannot be restarted or overwritten through the run store. Analyst status and ownership live in separate tables. Viewing a historical scan uses its stored assessments and policy outcomes, so later risk rules do not change historical risk. Explicit scan deletion remains available through the existing scan history controls.

The status flow is `New → Reviewed → Accepted for Migration → In Progress → Mitigated → Verified → Closed`. A Security Engineer may select `Risk Accepted` from any nonterminal step by recording a reason. The API requires the current version for every change and returns a five-second Undo token. Undo belongs to the same server-authenticated principal and fails after expiry or any later edit. Existing legacy migration decisions map into the new flow; legacy `accepted` maps to `Reviewed` because it has no recorded acceptance reason.

To grant a role, provision a random token through a secret manager and configure `QRYPTON_ACCESS_TOKENS` as a JSON object keyed by the token's lowercase SHA-256 hex digest. Each value contains a `subject` and one of `Viewer`, `Executive`, `Security Engineer`, `Developer`, or `CI Publisher`. For example, generate a token with `python -c "import secrets; print(secrets.token_urlsafe(32))"`, hash it with `python -c "import hashlib,sys; print(hashlib.sha256(sys.argv[1].encode()).hexdigest())" TOKEN`, and store the mapping in the backend environment. Missing credentials are Viewer; an invalid supplied token is rejected. The sign-in form accepts a provisioned token, and a read-only Viewer path is available. The server validates the role on mutations; browser storage and UI controls do not grant permissions.

Use Ctrl/⌘ K to search pages, applications, scans, and findings across the workspace. Terms such as `internet-facing RSA critical` combine exposure, algorithm, and risk conditions. Results are capped at 100 and are reached with arrow keys and Enter. In lists, `j` and `k` move, Enter opens, and `e` opens a finding's status editor. In a finding detail, `j` and `k` move between sections and Enter opens the focused section's first control. `?` opens shortcut help. The full finding page's Back to filtered list link carries the selected scan and inventory filters.

The dashboard home shows the same posture, priority, and integrations panels in an order determined by the authenticated role. Developer PR/CI results come from `GET /api/v1/integrations/ci-results`; the panel shows a truthful empty state until results arrive. A CI integration submits `POST /api/v1/integrations/ci-results` with a dedicated `CI Publisher` bearer token and JSON fields `provider`, `external_id`, `repository`, `title`, `ref`, `result` (`success`, `failure`, `cancelled`, or `pending`), `url` (HTTPS), `completed_at` (timezone-aware ISO 8601), and optional `run_id`. The tuple `(provider, repository, external_id)` is idempotent within a tenant; conflicting revisions return 409. A referenced scan must belong to the tenant. CI Publisher cannot change finding status. Simple/Detailed changes the amount of panel detail. Glossary definitions are available by hover or keyboard focus, with Escape dismissing the card.
